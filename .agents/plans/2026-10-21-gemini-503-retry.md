## Task Summary
A search failed with Gemini's raw error:

```
{"error":{"code":503,"message":"This model is currently experiencing high demand. Spikes in demand are usually temporary. Please try again later.","status":"UNAVAILABLE"}}
```

**The fix has two parts:**
1. Retry a Gemini **503 UNAVAILABLE** a couple of times with a short back-off, the same way a per-minute 429 is retried today.
2. If it still fails, show a readable message on the failed search instead of the JSON.

## Root cause (stated before fixing, per the bug protocol)
- **No retry:** `lib/ai/gemini.ts` only retries when `parseRateLimit(err)` recognises a 429. Every other `ApiError`, 503 included, is thrown on the first attempt (the "Any other error … not retried" rule from the 429 plan).
- **The SDK's own retry** (`httpOptions.retryOptions`) is still off. We keep it off, for the same reasons as in the 429 plan.
- **Why a 503 fails the whole search:**
  - When the Query field is blank, the first AI call is `deriveQueriesFromCv` (`lib/derive-query.ts:15`). It has no catch, so its error reaches `runSearch`'s catch, and the search is saved as `failed`.
  - A 503 during **scoring** doesn't fail the search: `scoreBatch` catches it and the batch's jobs end up unscored.
- **Why the JSON is shown:**
  - `searchErrorMessage` (`lib/search-errors.ts`) only rewrites timeouts and aborts.
  - The SDK's `ApiError.message` is the JSON error body, so that's what gets stored and shown.
- **Not confirmed:** which step failed. That needs the server log line `run_search.failed`. The fix covers every Gemini call either way.

## Affected Files
- **`lib/ai/gemini-retry.ts`:** a new pure helper, `isOverloaded(err)`. It's true for an `ApiError` with `status === 503`, or a message containing `"UNAVAILABLE"`, mirroring how `parseRateLimit` checks for `RESOURCE_EXHAUSTED`.
- **`lib/ai/gemini.ts`:** the existing retry loop also retries when `isOverloaded(err)`. The back-off is 2 s then 4 s, plus 0–1 s jitter.
- **`lib/search-errors.ts`:**
  - new `AI_BUSY_MESSAGE` = "The AI provider is busy right now. Please try again in a few minutes.";
  - `searchErrorMessage` returns it for a Gemini 503, and for Anthropic's overloaded error (status 529, `overloaded_error`) if you say yes to Question 2.
- **Tests:**
  - `tests/unit/gemini-client.test.ts`: new cases; the existing ones stay;
  - `tests/unit/gemini-retry.test.ts`: `isOverloaded` cases;
  - `tests/unit/job-sources-country.test.ts`: the existing `searchErrorMessage` block gets a busy-message case.
- **Docs:** this plan and its review.

## Current Behavior to Preserve (`createGeminiClient().complete`, from the 429 plan)
1. Model per tier, `thinkingLevel: LOW`, `maxOutputTokens`, `systemInstruction`, JSON mode: the request is unchanged.
2. `completionSignal({ signal, timeoutMs })`: cancel and timeout still end the call, including any wait.
3. **Per-minute 429:** wait Gemini's `retryDelay`, at most 2 retries, never past the deadline. Unchanged.
4. **Per-day 429:** no retry. Unchanged.
5. **Empty response:** `'Gemini: empty response'`, not retried. Unchanged.
6. **Every other error** (400, 401, 404, 500, 504, network) is still thrown without retry. Only 503 is new.
7. **`searchErrorMessage`:**
   - timeouts and aborts → `AI_TIMEOUT_MESSAGE`;
   - other errors keep their own message (for example "Add an Anthropic or Gemini API key in Settings");
   - a non-Error → 'Unknown error'.

`deriveQueriesFromCv`, `scoreBatch` and the other callers are **not changed**. They benefit automatically.

## Out of Scope
- **Retrying 500 or 504.** Google suggests retrying those too, but we haven't seen them. See Question 1.
- **A fallback in `deriveQueriesFromCv`** when the AI call fails, for example using the CV's most recent role. That would let the search carry on, but it changes search behaviour; it's a separate follow-up.
- **Falling back to the other AI provider** (Gemini → Anthropic) when one is down.
- **Anthropic retries:** its SDK already retries 429, 5xx and 529 (`maxRetries` 2).
- **Readable errors on other routes** (CV parse, deep-dive, cover letter). Only the search's stored error changes here.

## Approach
1. **Reproduce.** Write the new `gemini-client` tests (below) and run them, after asking. The 503 retry cases should fail on today's code: `generateContent` is called once and the 503 is thrown.
2. **Confirm** the root cause with you, then fix.
3. **`isOverloaded(err)`** in `gemini-retry.ts`, next to `parseRateLimit`.
4. **The loop in `complete()`.** The current branch logic is:
   ```
   limit = parseRateLimit(err)
   if limit and !limit.perDay → wait limit.retryAfterMs + jitter
   ```
   It becomes:
   ```
   limit = parseRateLimit(err)
   if limit and !limit.perDay   → wait = limit.retryAfterMs + jitter   (as today)
   else if isOverloaded(err)    → wait = OVERLOAD_BACKOFF_MS[attempt] + jitter   // [2_000, 4_000]
   else                         → throw err
   if attempt >= MAX_RATE_LIMIT_RETRIES or now + wait >= deadline → throw err
   ```
   - Both kinds share the same 2-retry cap. So it's still at most 3 attempts per call.
   - Each retry logs `gemini.overloaded { attempt, waitMs, retrying }` at `warn`. When it gives up, it logs once with `retrying: false`.
   - The constant keeps its name (`MAX_RATE_LIMIT_RETRIES`) to keep the diff small, and its comment is updated. I can rename it to `MAX_RETRIES` if you prefer.
5. **`searchErrorMessage`.** Before the final `return err.message`, map a 503 (`status === 503`, or a message containing `"UNAVAILABLE"`) to `AI_BUSY_MESSAGE`, plus 529/`overloaded_error` if you say yes to Question 2. It reuses `isOverloaded` from `gemini-retry.ts`.

## Edge Cases & Risks
- **Timeouts:** derive-query has 30 s, a scoring batch 45 s. The worst case of both waits is 2 + 4 + 2 s of jitter = 8 s, plus the three attempts themselves, which fits. When a wait wouldn't fit before the deadline, the call fails at once, as with 429.
- **Longer outages:** if Gemini stays overloaded, every call now takes up to about 8 s longer before failing. For a search, that means scoring batches finish as unscored a little later; the 300 s search budget is still respected.
- **More load on an overloaded model:** at most 2 extra requests per call, with jitter, so retries don't land at the same moment. This follows Google's guidance (retry with back-off).
- **Cancel during a wait:** the abortable `sleep` rejects with the abort reason, as today.
- **String match on "UNAVAILABLE":** it's only used when the status is missing, the same pattern as `RESOURCE_EXHAUSTED`. A 503 always carries the status in the SDK's `ApiError`.

## Testing Strategy (failing tests first)
**Reproduce** (`gemini-client.test.ts`, SDK mocked, fake timers). These fail today:
- one 503 then success → returns the text; 2 calls; waited about 2 s;
- two 503s then success → 3 calls;
- three 503s → throws the 503 after the 3rd call;
- a 503 when the call's `timeoutMs` leaves no room for the wait → throws at once, after 1 call;
- cancelled during the 503 wait → rejects with the abort reason;
- a mix: a per-minute 429, then a 503, then success → 3 calls; the cap is shared.

**Must not change** (passing today, kept):
- per-day 429, 400, empty response: 1 call;
- a 500 is also thrown after 1 call (new guard case).

**`isOverloaded`** (`gemini-retry.test.ts`):
- the real 503 body above → true;
- a 429, 400 or 500, a plain Error and a non-Error → false.

**`searchErrorMessage`:**
- the 503 `ApiError` → `AI_BUSY_MESSAGE`;
- the existing timeout and plain-message cases are unchanged.

**Regression:** lint, typecheck and the full `npm test`, after asking.

**Manual:** retry the search; when Gemini is overloaded, the logs show `gemini.overloaded` with `retrying: true`.
